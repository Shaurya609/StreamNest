### Approved website development brief — 20 November 2026

- **Design:** use the Cinematic concept selected by the owner, retaining StreamNest branding and a responsive layout. The Get started alternative is not the selected direction.
- **Screenshots:** capture real desktop and Android app screens for the landing page and illustrated guides. Hide personal watch history, pairing codes, group/device identifiers and other private information. Do not fabricate app screenshots.
- **Pages:** Home, Downloads, Guides, How it works, and Help/privacy. Explain torrent sources, peers, buffering and cache in plain language without promising every title/source will play.
- **Guides:** installation and updates on Windows/Android/TV/projector; named sync-group creation and joining by short code/QR; automatic resume and shared recommendations; optional next-episode preloading and previous-episode cleanup; cache-folder selection, USB requirements and Low Memory mode; subtitles/audio, playback troubleshooting and diagnostic/activity-sharing controls. Verify current UI labels and behavior while writing guides.
- **Downloads:** Get StreamNest suggests the Windows .exe installer or universal Android APK for compatible phones, tablets, Android TV/Google TV and Android projectors. Provide an always-visible device/platform override because detection can be wrong. Unsupported platforms receive compatibility information; do not imply an APK works on Tizen/webOS/iOS/macOS.
- **Direct delivery:** buttons point directly to the appropriate GitHub Release asset, triggering a browser download rather than navigating to the GitHub release page. Browser confirmation/download handling may still apply. Keep a separate release-notes/fallback link.
- **Hosting:** develop and publish through Sites; keep installers/APKs on GitHub Releases. Do not duplicate installer uploads on Sites. This is the approved approach, not an already deployed website.
- **Release freshness:** integrate the verified release feed with distinct Android and Windows versions/assets. Proposed workflow: publish and verify app assets, then update the feed; the website resolves the latest approved asset/version without a website redeploy for each app release. Validate feed compatibility, cache refresh, asset selection, unavailable-feed fallback and download behavior during implementation. Do not simply use GitHub's single latest-release pointer, since platforms release independently.
- **Website maintenance:** publish design, screenshot and guide changes through Sites separately from app releases. Keep secrets and the private owner dashboard out of public website source/content.
- **Current scope:** decisions saved only; do not begin website implementation or publication until the owner asks to start.

### Tracking rules

- Every open item belongs to owner testing or developer work. Link dependencies rather than combining both into an ambiguous pending item.
- Developer tests on the available tablet/laptop and log analysis belong to the developer backlog. Physical-device checks that need the owner's use belong to the owner backlog.
- Close owner-confirmed issues and record acceptance in VALIDATION.md. Do not reintroduce them from older notes.
- Source availability or missing provider timestamps are external limitations unless a concrete app defect or approved improvement is identified. Broader Korean dub/sub, filler and skip coverage do not become recurring generic backlog items without a specific failed case.
- Windows signing is intentionally out of scope. Personal subtitle-account retention is out of scope (anonymous access only). Cloudflare usage monitoring is routine operation, not backlog.
